# Gestión del Proyecto Académico

Este directorio contiene el cronograma, la organización, las responsabilidades, las actividades, las evidencias y los criterios de evaluación de Seminario de Actualización Tecnológica I.

El repositorio principal corresponde al producto denominado **Plataforma de Gestión y Consulta de Recolección de Residuos**. El desarrollo se realiza como un proyecto único de curso, organizado mediante células verticales y equipos horizontales.

## Actividades del estudiante

Durante las trece semanas de trabajo independiente, cada estudiante desarrolla actividades de organización, trabajo de campo, trabajo vertical en su célula, trabajo horizontal en los equipos transversales y trabajo individual de acuerdo con su rol.

La responsabilidad individual acompaña todas las fases. Ningún estudiante queda vinculado exclusivamente al diseño, al levantamiento de información, a la programación, a las pruebas o a la documentación.

## Organización del trabajo

### Células verticales

Las células verticales construyen los módulos funcionales del producto:

- Zonas, barrios y puntos de referencia.
- Vehículos y conductores.
- Rutas y horarios.
- Inicio de rutas y novedades.
- Consulta y reportes.

Cada célula participa en el análisis, diseño, desarrollo, pruebas, documentación e integración de su módulo.

### Equipos horizontales

Los equipos horizontales establecen y mantienen los lineamientos comunes:

- Arquitectura y backend.
- Datos y API.
- UX/UI y sistema de componentes.
- Calidad y testing.
- DevOps, Git y despliegue.
- Documentación e inteligencia artificial.

Cada estudiante pertenece a una célula vertical y desempeña una responsabilidad transversal en uno de estos equipos.

## Roles

La asignación de roles se realiza mediante un proceso individual de perfilamiento que considera conocimientos, habilidades, intereses y capacidad de aprendizaje.

Los roles establecidos son:

- Product Owner: docente responsable de la visión y priorización del producto.
- Líder funcional.
- Analista.
- Desarrollador frontend.
- Desarrollador backend.
- Responsable de datos.
- Diseñador UX/UI.
- Responsable de testing.
- Responsable de documentación.
- Responsable de DevOps y despliegue.
- Responsable de integración y calidad técnica.

## Gestión en GitHub

- Cada actividad se registra mediante una Issue.
- Cada Issue contiene objetivo, responsable, criterio de aceptación y evidencia.
- Cada desarrollo se realiza en una rama.
- Cada integración se ejecuta mediante un Pull Request.
- La rama `main` permanece estable.
- Las decisiones transversales requieren revisión del equipo horizontal correspondiente.
- Los commits deben ser frecuentes, comprensibles y atribuibles.
- Cada entrega se identifica mediante un tag o release.
- El GitHub Project concentra el seguimiento del trabajo.

## Evaluación

La evaluación es acumulativa y se consolida en tres reportes:

| Reporte | Porcentaje | Evidencia integradora |
|---|---:|---|
| Entrega 1 | 30 % | Problema validado, alcance, organización, UX/UI y arquitectura inicial |
| Entrega 2 | 30 % | Backend, base de datos, API, frontend integrado y avance funcional |
| Entrega 3 | 40 % | Producto publicado, pruebas, documentación y defensa técnica |

Cada reporte contiene varias actividades. Una actividad integradora de mayor peso cumple la función académica del parcial y puede repetirse cuando exista una situación de fuerza mayor debidamente justificada.

Al finalizar cada corte se consolida la calificación. Las actividades ordinarias de un corte no se trasladan al siguiente.

## Evidencias

- GitHub: Issues, commits, ramas, Pull Requests, documentos y releases.
- Teams: reuniones, entrevistas autorizadas, discusiones y acuerdos.
- Moodle: tres entregas formales.
- GitHub Project: priorización, estado y seguimiento.
- Bitácora de inteligencia artificial: consultas, decisiones, resultados aceptados y resultados descartados.
