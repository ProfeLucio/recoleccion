# Gestion del proyecto

## Modelo de trabajo

El curso funciona como una empresa academica. Todo el salon trabaja sobre un mismo producto y se organiza en celulas verticales y equipos horizontales.

## Responsabilidades verticales

Cada celula desarrolla un modulo funcional. Sus integrantes deben participar en:

- Comprension del problema.
- Levantamiento y refinamiento de requisitos.
- Diseno funcional y visual.
- Desarrollo frontend y backend.
- Pruebas.
- Documentacion.
- Integracion y defensa.

La especializacion ayuda a distribuir el trabajo, pero no exonera a ningun estudiante de comprender el producto completo.

## Responsabilidades horizontales

Los equipos horizontales definen lineamientos para todas las celulas:

| Equipo | Responsabilidad |
|---|---|
| Arquitectura y backend | Estructura del sistema, servicios y decisiones tecnicas |
| Datos y API | Modelo de datos, persistencia, endpoints y contrato API |
| UX/UI | Identidad, wireframes, componentes y consistencia visual |
| Calidad y testing | Casos de prueba, revision, bugs y criterios de aceptacion |
| DevOps e integracion | Ramas, Pull Requests, ambientes y despliegue |
| Documentacion e IA | README, decisiones, manuales y bitacora de IA |

## Criterio de asignacion

Los estudiantes se perfilan individualmente mediante formulario, actividad tecnica corta y conversacion de orientacion. La conformacion de celulas busca equilibrio de capacidades y no solamente afinidad personal.

## Reglas de GitHub

- Una Issue representa una actividad, historia, bug o decision.
- Toda Issue debe tener responsable y criterio de aceptacion.
- Cada cambio se desarrolla en una rama.
- Cada integracion se realiza mediante Pull Request.
- El equipo horizontal correspondiente revisa los cambios transversales.
- La rama `main` debe permanecer estable.
- Los commits deben describir cambios concretos.
- Las entregas se identifican mediante tags o releases.

## Evidencias

- GitHub: Issues, commits, Pull Requests, documentos y releases.
- Teams: reuniones, entrevistas autorizadas y acuerdos.
- Moodle: entregas formales y calificacion.
- GitHub Project: estado y priorizacion del trabajo.

## Ambientes

- Desarrollo: trabajo individual y de cada celula.
- Pruebas: integracion y validacion transversal.
- Produccion: demostracion del producto estable.

## Criterios de cierre de una tarea

Una tarea se considera terminada cuando:

1. Cumple su criterio de aceptacion.
2. Tiene evidencia verificable.
3. Fue revisada por otro integrante.
4. Esta integrada sin romper funcionalidades existentes.
5. Tiene la documentacion necesaria.
